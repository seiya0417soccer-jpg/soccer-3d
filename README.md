# 90秒スコアアタック × NavMesh連動 落下パズルバトル

Unityで制作した、オリジナルの2画面構成アクションパズルゲームです。

右画面の落下パズルでブロックを消すことで左画面の勇者を強化し、90秒間で何体の敵を倒せるかを競います。

NavMeshAgentを利用して、プレイヤーが直接操作しなくても自律的に戦闘する勇者を作りたいという発想から制作を始めました。

しかし、勇者が自動で戦うだけではプレイヤーが介入する余地が少ないと考え、落下パズルを組み合わせました。

プレイヤーのパズル操作が勇者の戦闘能力に影響することで、2つのシステムが連動するゲーム構成にしています。

また、初期開発ではゲームを完成させることを優先しましたが、その後、機能追加に伴う依存関係の複雑化を課題として認識し、既存コードの設計改善にも取り組んできました。

---

## 🎮 ゲーム概要

* **ジャンル：** スコアアタック × 落下パズル × 自律戦闘
* **開発環境：** Unity 2022.3
* **プログラミング言語：** C#
* **制作開始：** 2025年2月26日
* **メインプロジェクト：** [soccer-3d](https://github.com/seiya0417soccer-jpg/soccer-3d)

### ゲームの基本ループ

1. 右画面の落下パズルを操作する
2. ブロックを消して勇者を強化する
3. 勇者がNavMeshAgentを利用して自律的に敵と戦う
4. 90秒間で倒した敵の数をスコアとして記録する
5. リザルト画面で結果を確認し、再挑戦する

### 主な特徴

* パズルと自律戦闘を組み合わせた2画面構成
* NavMeshAgentによる敵の探索・追跡・攻撃
* ブロック消去による勇者の強化
* 爆弾によるブロック消去と戦闘能力への影響
* 制限時間内の撃破数を競うスコアアタック
* バフ・デバフや敵撃破に連動した演出
* オンラインランキング機能

# ⚔ 主な実装内容

## 1. 勇者の自律戦闘AI

NavMeshAgentを利用し、プレイヤーが直接操作しなくても敵を探索して戦闘する仕組みを実装しました。

### 主な機能

* 周囲の敵の探索
* 敵への自動移動
* 攻撃距離に応じた攻撃処理
* 敵撃破処理
* 敵撃破時のスコア加算
* 攻撃・移動アニメーションの制御
* 敵撃破時のカメラシェイク

プレイヤーが直接勇者を操作するのではなく、パズルの結果を通して戦闘に介入する仕組みにしています。

## 2. オリジナル落下パズル

落下型パズルをベースに、ゲーム独自の要素を追加しました。

### 主な機能

* ピースの生成・管理
* ブロックの落下処理
* ライン消去処理
* 特殊ブロックの管理
* 浮き島の検出と落下演出
* ブロック消去数に応じた勇者の強化

パズル側とバトル側を連動させることで、パズルの操作結果が自律戦闘の結果に影響するゲーム構成にしています。

## 3. 爆弾システム

異なる効果を持つ2種類の爆弾を実装しました。

### CrossBomb

特殊ブロックとして生成される爆弾です。

* 十字方向のブロックを消去
* 条件に応じた連鎖消去

### EKeyBomb

プレイヤーが任意のタイミングで使用できる爆弾です。

* 5×5範囲のブロックを消去
* 使用後に勇者へデバフを付与

強力な消去効果だけでなく、使用後にデメリットを設けることで、リスクとリターンを持たせました。

## 4. バフ・デバフと演出

パズルの結果や爆弾の使用によって、勇者の戦闘能力が変化します。

### 主な実装

* ブロック消去による移動速度の強化
* EKeyBomb使用後の移動速度低下
* バフ発生時の発光演出
* デバフ発生時の発光演出
* 敵撃破時のカメラシェイク

状態変化を発光などの演出で表現し、プレイヤーがゲーム内の変化を把握しやすいようにしました。

また、バフとデバフの処理が互いに干渉する箇所についても、状態管理の責務を整理する改善に取り組んでいます。

## 5. ゲーム進行管理

タイトル画面からゲームプレイ、リザルト画面までの進行を管理しています。

Stateパターンを利用し、ゲームの進行状態ごとに処理を分離しました。

### 主な状態

* `TitleState`
* `ManualState`
* `CountdownState`
* `PlayingState`
* `GameOverState`
* `FinishState`
* `ResultState`

状態ごとに処理を分離することで、ゲーム進行の見通しを良くし、各状態の変更に対応しやすい構造を目指しました。

# 🌐 オンラインランキング機能

技術検証プロジェクトOtamesiで試したDocker環境上のAPIとの連携を、本制作にも応用しました。

UnityからランキングAPIと通信し、ゲームのプレイ結果を外部のシステムと連携させる機能を実装しています。

### 主な構成要素

* `IScoreRepository`
* `ApiScoreRepository`
* `IScoreApiClient`
* `DockerScoreApiClient`
* `FakeScoreApiClient`

### 設計上の工夫

* ランキングデータを扱う処理とAPI通信を分離
* Interfaceを介してAPIクライアントへの依存を抽象化
* ランキング処理と通信処理の責務を分離
* APIクライアントを差し替えられる構成

ランキング機能をゲーム本体の処理から分離し、外部通信に関する変更の影響範囲を抑えられる構造を目指しました。

また、API通信を抽象化することで、実際の通信処理とテスト用の代替実装を切り替えられるようにしています。

この機能を通して、Unity内のゲームロジックだけでなく、外部APIとの通信やデータの受け渡しを含む機能の実装を経験しました。

# 🏗 設計改善への取り組み

## 1. 既存コードの依存関係を見直す

開発初期はゲームを完成させることを優先したため、機能が増えるにつれてクラス間の依存関係が複雑になりました。

そこで、ゲームを作り直すのではなく、既存コードを段階的に改善する方針を取りました。

### 改善で意識したこと

* クラスごとの責務を明確にする
* 依存関係を把握しやすくする
* 機能追加や変更の影響範囲を抑える
* 他の開発者が理解しやすい構造にする
* 将来の仕様変更に対応しやすくする

設計パターンやライブラリを導入すること自体を目的にせず、既存コードの課題に対して必要な方法を選択することを意識しています。

## 2. VContainerによる依存関係の管理

VContainerを導入し、依存関係を管理する構造へ改善しました。

### 主な取り組み

* 依存関係の注入
* Interfaceを介した依存先の抽象化
* LifetimeScope・Installerによる依存関係の登録
* 機能ごとの依存関係の整理

依存先の生成や登録を各クラスに分散させず、DIコンテナ側で管理することで、依存関係を追いやすい構成を目指しました。

また、DIコンテナを導入する前に、既存クラスの役割やオブジェクトの管理方法を整理する段階も設けました。

Singletonを一律に否定するのではなく、オブジェクトの管理方法を検討しながら、依存関係の管理を改善しています。

## 3. R3によるイベント駆動化

パズル側とバトル側が互いの実装を直接参照しないよう、R3を利用したイベント通知を導入しました。

例えば、パズルでブロックが消去された際、パズル側が勇者の速度を直接変更するのではなく、消去に関する通知を発行し、バトル側が通知を受けて強化処理を行います。

### 設計上の狙い

* パズル側とバトル側の責務を分離する
* 直接参照による依存を減らす
* 変更時の影響範囲を抑える
* システム間の連携を明確にする

イベント通知の導入にあたっては、購読解除や破棄時の処理にも注意し、オブジェクトの寿命に合わせた管理を意識しています。

## 4. Interfaceによる抽象化

システム間の依存関係を整理するため、Interfaceを利用しています。

| Interface      | 役割              |
| -------------- | --------------- |
| `IPuzzleField` | パズルシステムとの連携を抽象化 |
| `IBattleField` | バトルシステムとの連携を抽象化 |
| `IScoreReader` | スコアの読み取りを抽象化    |
| `IScoreWriter` | スコアの書き込みを抽象化    |

例えば、スコアの読み取りと書き込みを分けることで、各クラスが必要とする操作だけに依存できる構造を目指しました。

Interfaceによる抽象化は、すべてのクラスに一律に適用するのではなく、システム間の依存関係や責務を整理する必要がある箇所で利用しています。

## 5. ScriptableObjectによるデータ管理

ゲームバランスや挙動に関する設定をScriptableObjectに分離しました。

### 主な管理対象

* 勇者の設定
* 敵の設定
* バトル関連の設定
* カメラ関連の設定
* パズル関連の設定

パラメータをコードから分離することで、ソースコードを直接変更せずに数値を調整できる構造にしています。

## 6. ゲーム進行と依存関係の整理

ゲーム進行はStateパターンで管理し、各機能の依存関係はVContainerのLifetimeScope・Installerを利用して登録しています。

ゲームの状態管理とオブジェクトの依存関係管理をそれぞれ整理することで、機能ごとの責務や接続関係を把握しやすい構造を目指しました。

# 🤖 Jevを活用したAIプレイテスター

Jevとの連携を利用し、落下パズルの自動プレイ機能を開発しています。

目的は、AIにゲームを操作させることだけではありません。将来的には、ゲームプランナーがゲームバランスを確認する際に活用できる開発支援ツールへ発展させることを目指しています。

## 開発の背景

ゲームバランスを検討する際には、さまざまな操作や配置を試し、ゲームの挙動を確認する必要があります。

そこで、AIによる自動プレイを活用し、手動操作以外の方法でもゲームをプレイできる仕組みを考えました。

## 基本的な設計方針

* 既存の落下パズルのルールを利用する
* ゲーム独自のピース形状に対応する
* 配置可能な候補を生成する
* Jevに配置と回転の判断を問い合わせる
* AIの判断をゲーム側で検証してから実行する
* AIの判断処理と既存のパズルロジックを分離する

標準的なテトリスのピースを前提にするのではなく、対象ゲーム独自のピース形状と既存のルールを利用する方針です。

また、AI連携の処理をパズル本体へ直接組み込むのではなく、ゲーム側の自動操作機能とAIによる判断処理を分離する構成を目指しています。

## 現在の取り組み

配置候補からAIに判断させ、ゲーム側でその選択を検証して実行する基本的な自動プレイ機能を中心に開発しています。

複雑な特殊ギミックまで最初から最適化するのではなく、まず基本的な配置判断を行う範囲に絞り、既存ゲームとの連携を成立させることを優先しています。

## 今後の展望

将来的には、自動プレイの結果を記録・比較し、パラメータ調整やゲームバランスの検討を支援できる仕組みへ発展させたいと考えています。

例えば、複数回のプレイ結果を比較し、設定変更によってゲームの挙動がどのように変化するかを確認できる仕組みを検討しています。

ただし、自動プレイ機能と統計的なバランス検証機能は別の段階です。結果の蓄積・分析などは、今後の発展課題として扱っています。
